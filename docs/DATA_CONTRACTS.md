# Agencia Automatizada MVP — Data Contracts

**Status:** Proposed for MVP-0
**Product:** Agencia Automatizada
**Department:** Trading
**Initial instrument:** XAU/USD
**Primary active agent:** Market Intelligence Agent
**Repository:** `Agencia-automatizada-MVP`

---

## 1. Purpose

This document defines the canonical data contracts for MVP-0.

It is the source of truth for the structured data exchanged between:

```text
Frontend
  ↓
API
  ↓
Application Layer
  ↓
Market Intelligence Agent
  ↓
Market Data Provider
  ↓
LLM Provider
  ↓
Persistence
  ↓
WebSocket notifications
```

The contracts defined here must remain independent from any specific frontend framework, LLM provider or market-data provider.

This document defines:

* request and response structures;
* market-data structures;
* market-analysis structures;
* persistence-facing operational state;
* WebSocket event structures;
* error envelopes;
* validation rules;
* identifiers;
* timestamps;
* provenance;
* lifecycle states;
* versioning rules.

This document does **not** define:

* trading strategies;
* BUY/SELL decisions;
* portfolio positions;
* order execution;
* broker contracts;
* deterministic risk calculations;
* backtesting contracts;
* multi-agent committee contracts.

Those belong to future MVPs.

## 2. Contract ownership

The LLM produces candidate structured content; the application layer produces the authoritative accepted contract.

The following ownership rules are mandatory.

### Backend authority

The backend is authoritative for:

* analysis identifiers;
* lifecycle state;
* timestamps generated by the system;
* persistence state;
* provider execution state;
* validation results;
* error state.

The frontend must never invent or overwrite these values.

### LLM authority

The LLM may generate interpretive analysis fields.

The LLM must **not** be authoritative for:

* `analysis_id`;
* lifecycle `status`;
* persistence state;
* execution state;
* provider provenance;
* system timestamps;
* API success/failure;
* trading execution;
* financial risk limits.

The application layer validates the LLM result before persistence.

### Provider authority

A market-data provider is authoritative only for the market data it actually returned.

Provider data must be validated before being passed to the agent.

## 3. Serialization conventions

### 3.1 JSON

External API and WebSocket contracts use JSON.

Field names use `snake_case`.

Example:

```json
{
  "analysis_id": "7c2e1ef6-1c88-4a3a-87f5-f3d5c9a0f11e",
  "timestamp_utc": "2026-09-18T14:30:00Z",
  "symbol": "XAUUSD"
}
```

### 3.2 Identifiers

System-generated entity identifiers use UUID v4 strings.

Required format:

```text
xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx
```

At minimum, the following identifiers must be UUIDs:

* `analysis_id`;
* `event_id`;
* `request_id`.

Identifiers must be unique within their respective domains.

### 3.3 Timestamps

All system timestamps are UTC.

External representation:

```text
ISO-8601 / RFC 3339
```

Example:

```text
2026-09-18T14:30:00Z
```

The backend must never expose local timezone timestamps as authoritative system timestamps.

### 3.4 Timestamp semantics

The following timestamp fields have precise meanings:

* `AnalysisRun.created_at_utc` = creation of the AnalysisRun record (status = pending)
* `AnalysisRun.started_at_utc` = beginning of execution (status = running)
* `AnalysisRun.completed_at_utc` = successful completion (status = completed)
* `AnalysisRun.failed_at_utc` = failed completion (status = failed)
* `MarketAnalysis.timestamp_utc` = timestamp assigned by the backend to the finalized successful analysis
* `MarketSnapshot.as_of_utc` = the market-data observation time
* `DataSource.source_as_of_utc` = the source data timestamp
* `DataSource.retrieved_at_utc` = when the provider returned the data
* `ModelMetadata.generated_at_utc` = when the model generated the interpretation

For completed analyses, `MarketAnalysis.timestamp_utc` MUST equal `AnalysisRun.completed_at_utc`.

### 3.5 Decimal values

Financial and market prices must not rely on binary floating-point semantics for persistence or contract validation.

JSON market-price fields must be represented as decimal strings.

**DecimalString definition:**

A `DecimalString` is a string matching the regex:

```text
^(0|[1-9]\d*)(\.\d+)?$
```

This represents a non-negative decimal number with no leading zeros (except for zero itself), optional fractional part, and no exponent notation.

For fields that must be strictly positive (prices), the value must be > 0.

For fields that may be zero (volume), the value must be >= 0.

Example:

```json
{
  "bid": "3642.15",
  "ask": "3642.25",
  "mid": "3642.20",
  "volume": "1234.56"
}
```

The backend may internally use `Decimal`.

### 3.6 Nullability

A field is either:

* required and non-null;
* optional and nullable;
* optional and omitted when unavailable.

The implementation must not use empty strings as substitutes for missing values.

## 4. Canonical enums

### 4.1 Instrument

MVP-0 supports one canonical instrument:

```text
XAUUSD
```

Human-readable UI may display:

```text
XAU/USD
```

The API and persisted contract use:

```text
XAUUSD
```

### 4.2 Timeframe

Supported MVP-0 values:

```text
1m
5m
15m
1h
4h
1d
```

The implementation may initially expose only the timeframe supported by the fixture provider.

Unsupported timeframes must return a validation error rather than silently changing the request.

### 4.3 Analysis status

```text
pending
running
completed
failed
```

State transitions:

```text
pending → running
running → completed
running → failed
```

Terminal states:

```text
completed
failed
```

A completed or failed analysis must never transition back to running or pending.

`pending` is a persisted backend state created when the analysis run record is first inserted. `running` begins when execution actually starts. Frontend-only states such as `idle` and `submitting` are not backend states and must not appear in the API or persistence contracts.

### 4.4 Data source mode

Internal provider metadata may use:

```text
fixture
live
```

This value identifies the provenance of the data.

It must not be interpreted by the frontend as a trading-quality guarantee.

### 4.5 Event types

MVP-0 defines:

```text
analysis.started
analysis.completed
analysis.failed
```

No trading-execution event types are allowed in MVP-0.

## 5. AnalysisRequest

`AnalysisRequest` represents the user/application request to perform a market analysis.

### Fields

| Field        | Type        | Required | Description                                          |
| ------------ | ----------- | -------: | ---------------------------------------------------- |
| `symbol`     | `string`    |      yes | Canonical instrument identifier                      |
| `timeframe`  | `Timeframe` |      yes | Requested analysis timeframe                         |
| `data_mode`  | `string`    |      yes | Data source mode: `fixture` or `live`                |

### Constraints

`symbol`:

```text
XAUUSD
```

`timeframe` must be one of the supported enum values.

`data_mode` must be one of:

```text
fixture
live
```

MVP-0 initially supports `fixture` mode. `live` mode is a valid contract value but returns an explicit provider-unavailable error until a live provider is configured. The backend must never silently substitute fixture data when `live` is requested.

The request does **not** include:

* model selection;
* prompt text;
* lifecycle state;
* provider credentials;
* broker information;
* position information;
* trading action.

Provider and model selection are application configuration concerns.

### Example

```json
{
  "symbol": "XAUUSD",
  "timeframe": "1h",
  "data_mode": "fixture"
}
```

## 6. MarketBar

`MarketBar` represents one OHLCV market-data interval.

### Fields

| Field           | Type            | Required |
| --------------- | --------------- | -------: |
| `timestamp_utc` | `datetime`      |      yes |
| `open`          | `DecimalString` |      yes |
| `high`          | `DecimalString` |      yes |
| `low`           | `DecimalString` |      yes |
| `close`         | `DecimalString` |      yes |
| `volume`        | `DecimalString` |      yes |

### Validation

For every valid bar:

```text
high >= max(open, close)
low  <= min(open, close)
high >= low
volume >= 0
```

The timestamp must represent the beginning of the bar interval.

A collection of bars must satisfy:

* strictly increasing timestamps;
* no duplicate timestamps;
* no malformed price values;
* no missing required OHLC fields.

A provider must not silently repair invalid bars.

Invalid provider data results in a provider/data-validation failure.

## 7. MarketSnapshot

`MarketSnapshot` represents the validated market state supplied to the Market Intelligence Agent.

### Fields

| Field         | Type            | Required | Description                             |
| ------------- | --------------- | -------: | --------------------------------------- |
| `symbol`      | `string`        |      yes | Canonical instrument                    |
| `timeframe`   | `Timeframe`     |      yes | Snapshot timeframe                      |
| `as_of_utc`   | `datetime`      |      yes | Market-data timestamp                   |
| `bid`         | `DecimalString` |      yes | Bid price                               |
| `ask`         | `DecimalString` |      yes | Ask price                               |
| `mid`         | `DecimalString` |      yes | Mid price                               |
| `bars`        | `MarketBar[]`   |      yes | Historical bars supporting the analysis |
| `data_source` | `DataSource`    |      yes | Provenance of the market data used for this snapshot |

### Price validation

The following invariants must hold:

```text
bid > 0
ask > 0
mid > 0
ask >= bid
```

The expected relationship is:

```text
mid = (bid + ask) / 2
```

The backend may calculate `mid` instead of trusting a provider-supplied value.

### Historical bars

The bars included in the snapshot must belong to the requested symbol and timeframe.

The agent must never receive bars from a different symbol or timeframe under the requested contract.

### Provenance relationship

For MVP-0, `MarketAnalysis.data_sources` MUST include the `MarketSnapshot.data_source`. The `MarketSnapshot.data_source` identifies the source of the snapshot itself. `MarketAnalysis.data_sources` is the analysis-level provenance collection designed to support additional context sources in future MVPs, but for MVP-0 it must contain at least the snapshot's data source.

| `provider_version` | `string`          |      yes |
| `retrieved_at_utc` | `datetime`        |      yes |
| `source_as_of_utc` | `datetime`        |      yes |

Example:

```json
{
  "mode": "fixture",
  "provider_name": "FixtureMarketDataProvider",
  "provider_version": "1.0.0",
  "retrieved_at_utc": "2026-09-18T14:30:01Z",
```

The system must never present fixture data as live market data.

## 9. MarketAnalysis

`MarketAnalysis` is the primary business result of MVP-0.

It combines validated market data with LLM-generated qualitative interpretation.

### Fields

| Field                 | Type                | Required |
| --------------------- | ------------------- | -------: |
| `schema_version`      | `string`            |      yes |
| `analysis_id`         | `UUID`              |      yes |
| `timestamp_utc`       | `datetime`          |      yes |
| `symbol`              | `string`            |      yes |
| `timeframe`           | `Timeframe`         |      yes |
| `market_snapshot`     | `MarketSnapshot`    |      yes |
| `trend_context`       | `TrendContext`      |      yes |
| `volatility_context`  | `VolatilityContext` |      yes |
| `key_levels`          | `KeyLevel[]`        |      yes |
| `market_observations` | `string[]`          |      yes |
| `uncertainties`       | `string[]`          |      yes |
| `data_sources`        | `DataSource[]`      |      yes |
| `model_metadata`      | `ModelMetadata`     |      yes |

### 9.1 TrendContext

```text
TrendContext:
  direction: up | down | sideways | unclear
  strength: weak | moderate | strong | unclear
  description: string
```

These are analytical interpretations, not deterministic trading signals.

`unclear` represents genuine analytical ambiguity and is not itself a failure. It indicates the LLM could not determine a clear direction or strength from the supplied data.

The `description` field must describe the analytical reasoning and must not contain trading instructions, entry/exit levels, position sizing, or broker/execution instructions.

### 9.2 VolatilityContext

```text
VolatilityContext:
  regime: low | moderate | high | unclear
  description: string
```

`unclear` represents genuine analytical ambiguity and is not itself a failure.

The `description` field must describe the analytical reasoning and must not contain trading instructions, entry/exit levels, position sizing, or broker/execution instructions.

### 9.3 KeyLevel

```text
KeyLevel:
  type: support | resistance
  price: DecimalString
  description: string
```

A key level is an analytical observation.

It must not be represented as a guaranteed support/resistance level.

Key level prices must be positive.

### 9.4 Market observations

`market_observations` contains concise qualitative observations grounded in the supplied snapshot.

Example:

```json
[
  "Price is trading above the recent short-term range midpoint.",
  "Recent candles show increasing directional persistence."
]
```

### 9.5 Uncertainties

`uncertainties` explicitly records limitations or ambiguous conditions.

Example:

```json
[
  "Historical sample does not include a major macroeconomic event window."
]
```

An empty array is valid when no material uncertainty is identified.

## 11. AnalysisRun

`AnalysisRun` represents the operational lifecycle stored in PostgreSQL.

### Fields

| Field                  | Type                       | Required |
| ---------------------- | -------------------------- | -------: |
| `analysis_id`          | `UUID`                     |      yes |
| `status`               | `AnalysisStatus`           |      yes |
| `created_at_utc`       | `datetime`                 |      yes |
| `started_at_utc`       | `datetime \| null`         |       no |
| `completed_at_utc`     | `datetime \| null`         |       no |
| `failed_at_utc`        | `datetime \| null`         |       no |
| `request_id`           | `UUID`                     |      yes |
| `request`              | `AnalysisRequest`          |      yes |
| `error`                | `ErrorDetail \| null`      |       no |
| `analysis`             | `MarketAnalysis \| null`   |       no |

### Lifecycle invariants

**pending** (record created, execution not yet started):

* `started_at_utc = null`
* `completed_at_utc = null`
* `failed_at_utc = null`
* `analysis = null`
* `error = null`
* `request` = the original `AnalysisRequest` that initiated the analysis

**running** (execution has begun):

* `started_at_utc != null`
* `completed_at_utc = null`
* `failed_at_utc = null`
* `analysis = null`
* `error = null`
* `request` = the original `AnalysisRequest` that initiated the analysis

**completed** (successful execution):

* `started_at_utc != null`
* `completed_at_utc != null`
* `failed_at_utc = null`
* `analysis != null`
* `error = null`
* `request` = the original `AnalysisRequest` that initiated the analysis

**failed** (execution failed):

* `started_at_utc != null`
* `completed_at_utc = null`
* `failed_at_utc != null`
* `analysis = null`
* `error != null`
* `request` = the original `AnalysisRequest` that initiated the analysis

A failed analysis must never contain a fabricated `MarketAnalysis`.

The `analysis` field contains the validated `MarketAnalysis` result when `status = completed`. The implementation may persist this as JSON/JSONB or equivalent. For `pending`, `running`, and `failed` statuses, `analysis` is null.

The `request` field contains the original `AnalysisRequest` in every lifecycle state, ensuring the request that initiated the analysis remains associated with the run for persistence and audit purposes.

For completed analyses, `MarketAnalysis.timestamp_utc` MUST equal `AnalysisRun.completed_at_utc`.

## 12. WebSocketEvent

WebSocket events are notifications, not the source of truth.

### Envelope

```json
{
  "event_id": "8f0a7f29-0f8e-4b0f-93c7-f4c6e2bf56c2",
  "event_type": "analysis.completed",
  "occurred_at": "2026-09-18T14:30:05Z",
  "analysis_id": "7c2e1ef6-1c88-4a3a-87f5-f3d5c9a0f11e",
  "payload": {}
}
```

### Required fields

| Field         | Type        | Required |
| ------------- | ----------- | -------: |
| `event_id`    | `UUID`      |      yes |
| `event_type`  | `EventType` |      yes |
| `occurred_at` | `datetime`  |      yes |
| `analysis_id` | `UUID`      |      yes |
| `payload`     | `object`    |      yes |

### Event payloads

#### `analysis.started`

```json
{
  "status": "running"
}
```

#### `analysis.completed`

```json
{
  "status": "completed"
}
```

#### `analysis.failed`

```json
{
  "status": "failed",
  "error": {
    "code": "PROVIDER_ERROR",
    "message": "Market data provider failed."
  }
}
```

WebSocket events are notifications only. They are not the source of truth.

* `analysis.completed` communicates lifecycle completion only. The frontend must retrieve the authoritative `MarketAnalysis` through `GET /api/v1/market-analyses/{analysis_id}`.
* `analysis.failed` communicates lifecycle failure only. The payload may contain a safe, non-authoritative error summary for immediate UI feedback. The authoritative failure state and error details come from the persisted backend state retrieved through `GET /api/v1/market-analyses/{analysis_id}`. Do not duplicate the complete error contract in the WebSocket payload.
* WebSocket delivery is not guaranteed. If the frontend disconnects, it must reconcile via HTTP.

## 13. Error contract

All API errors use a common envelope.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Unsupported timeframe.",
    "details": {
      "field": "timeframe"
    }
  },
  "meta": {
    "request_id": "c9c52d62-5e0b-4a11-bc61-89e7a9f4e9b4"
  }
}
```

### Error codes

MVP-0 defines:

```text
VALIDATION_ERROR
CONFIGURATION_ERROR
PROVIDER_ERROR
LLM_ERROR
ANALYSIS_VALIDATION_ERROR
PERSISTENCE_ERROR
NOT_FOUND
UNEXPECTED_ERROR
```

Error messages must be safe for presentation.

Secrets, credentials, API keys and private model reasoning must never appear in error responses.

## 14. HTTP API contracts

### 14.1 Create market analysis

```text
POST /api/v1/market-analyses
```

Request:

```json
{
  "symbol": "XAUUSD",
  "timeframe": "1h",
  "data_mode": "fixture"
}
```

The backend:

1. validates the request;
2. creates the analysis identifier;
3. creates the operational run;
4. obtains market data;
5. validates the snapshot;
6. executes the Market Intelligence Agent;
7. validates the structured result;
8. persists the result;
9. emits the lifecycle events.

The response must contain the authoritative analysis identifier and lifecycle information.

### 14.2 Get market analysis

```text
GET /api/v1/market-analyses/{analysis_id}
```

Returns the persisted analysis and associated lifecycle state.

### 14.3 List analyses

```text
GET /api/v1/market-analyses
```

Returns historical analyses using server-side pagination.

The API must not return an unbounded number of records.

Pagination details may initially use:

```text
limit
offset
```

and can later be replaced by cursor-based pagination without changing the domain contract.

### 14.4 Successful response envelope

Successful API responses use:

```json
{
  "data": {},
  "meta": {
    "request_id": "UUID"
  }
}
```

`data` is always an object (never an array directly). It contains the resource payload appropriate to the endpoint.

`meta.request_id` identifies the HTTP request and is different from `analysis_id`.

### 14.5 Create response

`POST /api/v1/market-analyses` returns HTTP 201 Created only when the analysis operation has completed successfully and the successful result has been persisted.

If the analysis execution fails, the operation is still persisted with `status = failed`, but the POST request returns an appropriate non-2xx HTTP error response using the common error contract (see §13). The response body follows the error envelope; the HTTP status reflects the failure class (e.g., 502 for provider failure, 500 for unexpected internal failure).

**Do not return HTTP 201 with `status = failed`.**

MVP-0 execution is synchronous: the request returns only after the analysis has completed or failed. The WebSocket may emit lifecycle notifications during execution, but WebSocket delivery is not guaranteed and is not the source of truth. The final HTTP response reflects the authoritative persisted state.

The successful response contains:

```json
{
  "data": {
    "analysis_id": "UUID",
    "status": "completed"
  },
  "meta": {
    "request_id": "UUID"
  }
}
```

The client must use `analysis_id` to retrieve the authoritative analysis or error through `GET /api/v1/market-analyses/{analysis_id}`.

### 14.6 Get response

`GET /api/v1/market-analyses/{analysis_id}` returns:

```json
{
  "data": {
    "analysis_id": "UUID",
    "status": "pending | running | completed | failed",
    "analysis": {},
    "error": null
  },
  "meta": {
    "request_id": "UUID"
  }
}
```

The response is a discriminated union on `status`:

* `pending` → `analysis = null`, `error = null`
* `running` → `analysis = null`, `error = null`
* `completed` → `analysis = MarketAnalysis`, `error = null`
* `failed` → `analysis = null`, `error = ErrorDetail`

### 14.7 List response

`GET /api/v1/market-analyses` returns:

```json
{
  "data": {
    "items": [],
    "pagination": {
      "limit": 20,
      "offset": 0,
      "has_more": false
    }
  },
  "meta": {
    "request_id": "UUID"
  }
}
```

Each item in `items` is an `AnalysisSummary` (defined below).

### 14.8 AnalysisSummary

`AnalysisSummary` represents a historical analysis entry for list responses.

| Field               | Type              | Required |
| ------------------- | ----------------- | -------: |
| `analysis_id`       | `UUID`            |      yes |
| `symbol`            | `string`          |      yes |
| `timeframe`         | `Timeframe`       |      yes |
| `status`            | `AnalysisStatus`  | yes |
| `timestamp_utc`     | `datetime`        |      yes |
| `data_source_mode`  | `DataSourceMode`  |      yes |

`timestamp_utc` equals `AnalysisRun.created_at_utc`. This is the timestamp used for historical list display and ordering. It is distinct from `MarketAnalysis.timestamp_utc` (which equals `AnalysisRun.completed_at_utc` for completed analyses).

`data_source_mode` represents the originally requested `AnalysisRequest.data_mode` (`fixture` | `live`). It is obtained from `AnalysisRun.request.data_mode`, ensuring the field exists even if execution fails before obtaining a `MarketSnapshot` or `DataSource`. For completed analyses, the requested mode must match the effective provenance used by the analysis. There must never be silent substitution between `fixture` and `live`.

## 15. Validation rules

Validation occurs at multiple boundaries.

### Request validation

Validate before provider or LLM execution.

* API validates enum membership for `symbol`, `timeframe`, `data_mode`.
* Provider validates whether the selected provider actually supports the requested symbol/timeframe/data mode.
* Never silently substitute another timeframe or provider mode.

### Provider validation

Validate:

* symbol;
* timeframe;
* timestamps;
* OHLC relationships;
* positive prices;
* non-negative volume;
* ordering of bars.

### Market snapshot consistency

The following cross-field validations apply to `MarketSnapshot`:

* All bars must use the same `symbol` as the snapshot.
* All bars must use the same `timeframe` as the snapshot.
* The latest bar's `timestamp_utc` must be <= `snapshot.as_of_utc`.

### LLM output validation

Validate:

* schema version;
* required fields;
* enum values;
* string lengths;
* number/price formats;
* key-level structures;
* absence of forbidden trading-action fields (see §18 for reserved concepts that must not appear in MarketAnalysis);
* qualitative safety: `market_observations`, `uncertainties`, `trend_context.description`, `volatility_context.description`, `key_levels[].description` must describe observations, context, or uncertainty and must not contain direct trading instructions, entry/exit instructions, position sizing, order instructions, or broker/execution instructions. The presence of such content constitutes an `ANALYSIS_VALIDATION_ERROR`.

Array and string length limits:

* `market_observations`: minimum 0 items, maximum 20 items, maximum 500 characters per item.
* `uncertainties`: maximum 20 items, maximum 500 characters per item.
* `key_levels`: maximum 20 items.
* `description` fields (all): maximum 2000 characters unless otherwise specified.

An invalid LLM result must produce:

```text
analysis.failed
```

and must never be persisted as a successful `MarketAnalysis`.

### Persistence validation

Persist only data that has passed domain/application validation.

## 16. Provenance requirements

Every successful `MarketAnalysis` must identify:

```text
what data was used;
when that data represented;
which provider supplied it;
which model generated the interpretation;
which prompt version was used.
```

This provenance is required for reproducibility and later debugging.

Fixture analyses must remain distinguishable from live analyses throughout:

```text
provider → snapshot → analysis → persistence → API → frontend
```

No layer may remove the fixture/live distinction.



## 17. Versioning

Every persisted `MarketAnalysis` carries:

```text
schema_version
```

Initial value:

```text
1.0.0
```

Backward-compatible additions may increment the minor version:

```text
1.1.0
```

Breaking changes require a major version:

```text
2.0.0
```

The `schema_version` field uses semantic version format (MAJOR.MINOR.PATCH).

Breaking changes include:

* removing required fields;
* changing field meaning;
* changing field type incompatibly;
* changing enum semantics;
* changing timestamp meaning.

The backend must not silently reinterpret old persisted analyses under a new incompatible schema.

Historical data must remain readable or be migrated explicitly.

`MarketAnalysis.timestamp_utc` is the UTC timestamp assigned by the backend to the validated analysis result.

It represents when the system finalized the structured analysis result.

It is distinct from:

- `MarketSnapshot.as_of_utc`: the market-data observation time;
- `DataSource.source_as_of_utc`: the source data timestamp;
- `DataSource.retrieved_at_utc`: when the provider returned the data;
- `ModelMetadata.generated_at_utc`: when the model generated the interpretation.

For completed analyses, `MarketAnalysis.timestamp_utc` MUST equal `AnalysisRun.completed_at_utc`.

For MVP-0, `data_sources` contains the provenance records that contributed directly to the analysis.

Because MVP-0 uses one market-data source and no external-news source, a successful MVP-0 analysis will normally contain exactly one market-data provenance record.

`market_snapshot.data_source` identifies the source of the snapshot itself.

`MarketAnalysis.data_sources` is the analysis-level provenance collection and is designed to support additional context sources in future MVPs.

## 18. Reserved future contracts

The following concepts are intentionally reserved and must not be added to MVP-0 without a separate specification:

```text
Strategy
TradingSignal
RiskAssessment
Position
Order
Execution
BacktestResult
Portfolio
BrokerAccount
CommitteeDecision
DirectorDecision
```

In particular, `MarketAnalysis` must not gain fields such as:

```text
buy
sell
entry_price
stop_loss
take_profit
position_size
broker_order_id
```

simply because an LLM can generate them.

These belong to future, explicitly controlled contracts.

## 20. Contract acceptance criteria

`DATA_CONTRACTS.md` is considered accepted for MVP-0 when:

* every MVP-0 cross-layer payload has a defined contract;
* required and optional fields are explicit;
* enums are explicit;
* timestamps are UTC;
* financial values use deterministic decimal semantics;
* provider provenance is preserved;
* LLM output is structurally validated;
* lifecycle states are explicit;
* WebSocket events are explicitly typed;
* errors use a common envelope;
* fixture data cannot be presented as live data;
* frontend state is not authoritative;
* no trading execution contract exists in MVP-0;
* versioning rules are defined;
* the contracts are consistent with `MVP_SCOPE.md` and `ARCHITECTURE.md`.

## 21. Source of truth rule

The document hierarchy is:

```text
MVP_SCOPE.md
    ↓
ARCHITECTURE.md
    ↓
DATA_CONTRACTS.md
```

* `MVP_SCOPE.md` defines approved product scope;
* `ARCHITECTURE.md` defines approved system architecture;
* `DATA_CONTRACTS.md` is the source of truth for the exact data schemas and cross-layer payload shapes within that approved architecture.

`DATA_CONTRACTS.md` does not override product scope or architecture decisions.

When an implementation decision conflicts with this document, the hierarchy must be reviewed before code is written.

Code must not invent a new cross-layer contract without updating the appropriate specification first.
